## Root Cause
Confirmed consistent with the code review: `routes/eko_recharge.py` (`/api/recharge/initiate`, covering mobile/DTH/BBPS) debits PRC via a raw `db.users` `$inc` and never calls `create_service_charge_on_success`, nor does it route through `WalletServiceV2.debit` (which carries the universal 20% service-charge hook). Therefore no `redemption_service_charges` row is ever created for recharges, and production data shows exactly that (0 recharge-linked charges across 3820 total rows).

## Suggested Fix
This is a product/code decision, not an infra or data issue:
- If 20% service charges SHOULD apply to recharges: E1 must wire the recharge success path to `create_service_charge_on_success` (or route the debit through `WalletServiceV2.debit`) so recharges generate `redemption_service_charges` rows like other redemptions. Redeploy afterward.
- If recharges are intentionally exempt (they already carry `admin_charge_prc` ~20% + `processing_fee_prc`): no change needed — the current behavior is by design.
- Product owner should confirm which of the two is intended before any code change.

No production data was altered.
